## 问题分析

### 问题1：为什么 `@workgroup_size(1, 1, 64)` 的Z维度是64？

**核心原因：这是蒙特卡洛积分的方向采样需求**

多重散射的计算需要对整个半球进行积分（计算所有方向的散射贡献）。由于无法精确积分，采用**蒙特卡洛采样**方法，在半球面上均匀采样64个方向。

关键代码：
```wgsl
const direction_sample_count: f32 = 64.0;   // 方向采样数 = 64
const workgroup_size_z = 64u;               // Z维度线程数 = 64
```

**设计原理：**

| 参数 | 值 | 意义 |
|------|-----|------|
| LUT分辨率 | 32×32 | 需要计算1024个像素值 |
| dispatchWorkgroups | 32, 32, 1 | 启动1024个工作组 |
| workgroup_size | 1, 1, 64 | 每个工作组有64个线程 |
| 总线程数 | 32×32×64 = 65536 | 每个线程计算一个方向的散射 |

**为什么是64个方向？**

64是一个经验值，是**质量与性能的平衡点**：
- 方向越多，积分越精确，但GPU计算量越大
- 64个方向通过黄金螺旋采样（`compute_sample_direction`）可以覆盖半球的主要散射方向
- 对于预计算LUT来说，64方向采样的精度已经足够

### 问题2：`direction_index = global_id.z` 的编程意义

**这是一个巧妙的并行架构设计**：

```wgsl
@compute
@workgroup_size(1, 1, workgroup_size_z)  // 每个工作组：X=1, Y=1, Z=64
fn render_multi_scattering_lut(@builtin(global_invocation_id) global_id: vec3<u32>) {
    let direction_index = global_id.z;  // Z索引对应方向采样
    // ...
}
```

**整体并行架构：**

```
┌─────────────────────────────────────────────────────────────────┐
│                    dispatchWorkgroups(32, 32, 1)               │
│                                                               │
│  ┌─────────────┐ ┌─────────────┐ ... ┌─────────────┐         │
│  │ 工作组(0,0) │ │ 工作组(1,0) │     │ 工作组(31,31)│         │
│  │ LUT像素(0,0)│ │ LUT像素(1,0)│     │ LUT像素(31,31)│        │
│  ├─────────────┤ ├─────────────┤     ├─────────────┤         │
│  │ 线程z=0~63 │ │ 线程z=0~63 │     │ 线程z=0~63 │         │
│  │ 64个方向   │ │ 64个方向   │     │ 64个方向   │         │
│  └─────────────┘ └─────────────┘     └─────────────┘         │
└─────────────────────────────────────────────────────────────────┘
```

**`direction_index = global_id.z` 的作用：**

1. **区分同一工作组内的不同线程**：每个工作组有64个线程，`global_id.z` 的范围是0~63
2. **分配方向采样任务**：每个线程负责计算一个特定方向的散射亮度
3. **共享内存协作**：64个线程的结果存入共享内存，然后通过归约合并

### 问题3：并行归约循环的原理

```wgsl
for (var i = 32u; i > 0; i = i >> 1) {
    if direction_index < i {
        shared_multi_scattering[direction_index] += shared_multi_scattering[direction_index + i];
        shared_luminance[direction_index] += shared_luminance[direction_index + i];
    }
    workgroupBarrier();
}
```

**这是经典的二进制并行归约算法**：

| 迭代 | i | 合并操作 | 结果位置 |
|------|---|---------|---------|
| 第1轮 | 32 | [0]+[32], [1]+[33], ..., [31]+[63] | 结果存于 [0]~[31] |
| 第2轮 | 16 | [0]+[16], [1]+[17], ..., [15]+[31] | 结果存于 [0]~[15] |
| 第3轮 | 8 | [0]+[8], [1]+[9], ..., [7]+[15] | 结果存于 [0]~[7] |
| 第4轮 | 4 | [0]+[4], [1]+[5], [2]+[6], [3]+[7] | 结果存于 [0]~[3] |
| 第5轮 | 2 | [0]+[2], [1]+[3] | 结果存于 [0]~[1] |
| 第6轮 | 1 | [0]+[1] | 结果存于 [0] |

**归约过程可视化：**

```
初始: [0] [1] [2] [3] ... [63]  (64个方向的散射值)

i=32: [0+32] [1+33] [2+34] ... [31+63]  (32个部分和)
i=16: [0+16] [1+17] ... [15+31]        (16个部分和)
i=8:  [0+8] [1+9] ... [7+15]           (8个部分和)
i=4:  [0+4] [1+5] [2+6] [3+7]          (4个部分和)
i=2:  [0+2] [1+3]                      (2个部分和)
i=1:  [0+1]                            (最终总和)
```

**为什么这样设计？**

- **GPU并行特性**：所有线程同时执行，但只有满足条件的线程实际执行加法
- **共享内存效率**：`shared_multi_scattering` 是工作组共享内存，访问速度极快（~100x快于全局内存）
- **`workgroupBarrier()`**：确保每轮归约完成后再进行下一轮，防止数据竞争

```
├─────────────────────────────────────────────────────────────────────┤
│ Step 2: 并行归约（6轮）                                              │
│   每轮将数组大小减半，最终 shared[0] 包含64个方向的总和                │
├─────────────────────────────────────────────────────────────────────┤
│ Step 3: 线程z=0输出结果                                              │
│   direction_index > 0 的线程直接返回                                 │
│   线程z=0: 应用公式 L_ms = L_single / (1 - f_ms)                     │
│   写入 multi_scattering_lut[global_id.xy]                            │
└─────────────────────────────────────────────────────────────────────┘
```

**核心公式**（第520行）：
```wgsl
let luminance = shared_luminance[0] * (1.0 / (1.0 - shared_multi_scattering[0]));
```

这是多重散射的递归近似公式：`L_ms = L_single / (1 - f_ms)`
- `L_single`：单次散射亮度（所有方向的积分）
- `f_ms`：多重散射因子（决定能量在大气中的保留比例）
- 分母 `1 - f_ms` 表示能量泄漏，其倒数表示多重散射的放大效应
